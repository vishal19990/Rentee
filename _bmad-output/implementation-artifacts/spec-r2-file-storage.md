## Intent

**Problem:** All uploaded files live in MongoDB GridFS in an Atlas database shared with another app and capped at 512 MB (free tier). A leaked database credential exposes everything in one place. The human created a free Cloudflare account to store files separately (option B), keeping the AES-256-GCM encryption already added (`src/lib/file-crypto.ts`).

**Approach:** Add a storage layer that writes files to a **private Cloudflare R2 bucket** (S3-compatible API) when R2 is configured, and falls back to GridFS when it isn't. Reads look in R2 first and fall back to GridFS, so existing files keep working until a migration script moves them.

**Decisions:**
- **Config (env):** `R2_ENDPOINT` (e.g. `https://<account>.r2.cloudflarestorage.com`), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` (e.g. `rentee-files`). R2 is "configured" only when all four are set; otherwise GridFS as today. No public bucket URL, no presigned URLs: files are always fetched server-side and streamed through the existing authenticated (or token-checked) routes.
- **Client:** `@aws-sdk/client-s3` with `region: "auto"`, `endpoint: R2_ENDPOINT`, `forcePathStyle: true` (verify against installed SDK types). Created lazily, cached. Server-only module.
- **Object keys:** `<bucket-name>/<id>` mirroring today's GridFS buckets and ids: `documents/<ObjectId>`, `avatars/<ObjectId>`, `bills/<ObjectId>`, `tours/<ObjectId>`, `photos/<filename>` (property photos use their random filename). Content-Type stored as object metadata (for encrypted objects, `application/octet-stream` plus `x-amz-meta-content-type` with the real type if needed).
- **Encryption unchanged:** documents, avatars, bills are sealed with `sealForStorage` before upload and opened after download, exactly as now; photos and tours stay unencrypted (no personal data; tours are shareable).
- **Single seam:** implement R2 inside the existing modules so callers don't change — `src/lib/file-store.ts` (`saveFile`/`readFile`/`deleteFile` for bills, tours, avatars), `src/lib/document-store.ts` (documents), `src/lib/photo-store.ts` (property photos). Behaviour: save → R2 if configured else GridFS; read → R2 (if configured) then GridFS fallback; delete → both (ignore missing). Ids are still generated by the app (new ObjectId) so references in Mongo documents don't change.
- **Migration script** `scripts/move-files-to-r2.ts`: dry run by default (counts per bucket and total bytes), `--confirm` copies each GridFS file to R2 **byte-for-byte as stored** (already-encrypted stays encrypted; unencrypted sensitive files are copied as-is — tell the user to run `encrypt-files.ts` first, and the script warns if it finds unencrypted sensitive files), verifies by downloading from R2 and comparing SHA-256, then deletes the GridFS copy. Skips files already in R2. Safe to re-run. `--keep-gridfs` option copies without deleting. Prints a summary.
- **`encrypt-files.ts`** must keep working: it operates on GridFS; also make it handle files already moved to R2 (read from R2, re-encrypt, write back to the same key, verify) so the order of running the two scripts doesn't matter.
- **Health/visibility:** Settings page shows a small "File storage" line: "Cloudflare R2 (rentee-files)" or "Database (GridFS)", plus "Encryption: on/off" — no secrets displayed.
- **Cleanup script** `scripts/cleanup-demo.ts` deletes files through the same layer (R2 + GridFS).
- **Docs:** README section "File storage (Cloudflare R2)": bucket must stay private; token scoped to the one bucket with Object Read & Write; env vars locally and on Render (`render.yaml` entries with `sync: false`); order of steps (set env → deploy → run `encrypt-files.ts --confirm` → run `move-files-to-r2.ts --confirm`); free-tier limits.

**Always:** never log credentials; never expose bucket URLs or object keys to the browser beyond existing routes; all existing auth checks on file routes unchanged; GridFS fallback keeps old data working; tests don't need real R2.

**Never:** public bucket, presigned URLs, removing GridFS support, storing sensitive files unencrypted when FILES_ENCRYPTION_KEY is set, touching the user's real database or a real R2 bucket during development.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Not configured | no R2 env vars | everything uses GridFS exactly as before | N/A |
| Upload with R2 | R2 configured, upload Aadhaar PDF | object `documents/<id>` in R2 holds encrypted bytes; nothing new in GridFS | R2 error → upload fails with a clear message, no DB record left pointing at a missing file |
| Read old file | R2 configured, file only in GridFS | served from GridFS fallback | N/A |
| Read moved file | file in R2 | served from R2, decrypted if sensitive | missing everywhere → 404 |
| Delete | delete tenant document | removed from R2 and GridFS | missing → ignored |
| Migrate dry run | 5 GridFS files | counts + bytes per bucket, nothing changed | N/A |
| Migrate confirm | 5 GridFS files | all copied, SHA-256 verified, GridFS copies deleted; re-run copies 0 | verify mismatch → GridFS copy kept, error reported, exit code 1 |
| Unencrypted sensitive file during migration | document without RENC header, key set | warning recommending `encrypt-files.ts` first | N/A |

## Code Map
